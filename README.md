	<h3>What is it for, exactly?
	</h3>
	<p>Peace of mind! SHA256, SHA1 and MD5 hashes are used to verify that a file or group of files has not changed. Simple as that. This is useful, even crucial, in all kinds of situations where data integrity is important.
	</p>
	<p>For instance, these days, it's not uncommon to find MD5 hashes (and less rarely now, SHA256 hashes) published alongside downloads, even Windows downloads. This hash, <em>when used</em>, ensures that the file you downloaded is exactly the same file the author uploaded, and hasn't been tampered with in any way, Trojan added, etc.; even the slightest change in the data produces a <em>wildly</em> different hash.
	</p>
	<p>A file hash is also the best way to ensure your 3D Printed propeller blade hasn't been "redesigned" to self-destruct!
	</p>
	<p><img alt="checksum on my Windows desktop, hashing like crazy.." src="https://corz.org/windows/software/checksum/img/checksum_tool-tip-style_progress.jpg" title="for smaller files you won't be able to read this quickly enough. Weeeeeeh!"/>
	</p>
	<p>It's also useful if you want to compare files and folders/directories; using checksums is far more accurate than simply comparing file sizes, dates or any other property. For quick file compare tasks, there's also checksum's little brother; <a href="https://corz.org/windows/software/checksum/simple-checksum.php" title="drag-and-drop files onto its icon for launch-with-hash, or onto its window for immediate hashing, either SHA256, CRC32, MD5 or SHA1">simple checksum</a>, simply drag &amp; drop Two files for an instant hash-accurate comparison.
	</p>
	<p><img alt="peace of mind for your optical data media, with hashing" src="https://corz.org/windows/software/checksum/img/checksum_verify_disk.png" title="checksum or verify an entire drive with a single windows explorer menu command"/>
	</p>
	<p>If you burn a lot of data to CD or DVD, you can use checksum to accurately verify the integrity of your data right after a burn, and at any time in the future. If you distribute data in any way, maybe torrenteering your favourite things, run a file server of some kind, or just email a few files to your friends; hashes enable the person at the other end to be absolutely sure that the file arrived perfectly, 100% intact.
	</p>
	<p>As well as providing secure verification against tampering, virus infection, file (and backup file) corruption,  transfer errors and more, digital fingerprints can serve as an "early warning" of possible media failures, be they optical or magnetic. It was a hash failure that recently alerted me to a failing batch of DVD-R disks; I saved my fading data in time, and got a refund on the disks. I'll leave you to consider the million other uses. There's only one <em>reason</em>, though; <em>peace of mind.</em>
	</p>

	<h3>Introducing.. The Unified Hash Extension™<br/> <small>And</small> Multi-Hashing™..
	</h3>
	<p>checksum uses the MD5, SHA1 and SHA256 hashing algorithms, and can create <code>.md5</code> and <code>.sha1</code> and <code>.sha2</code> (or <code>.whatever</code> you use) files to contain these hashes. But checksum prefers to <em>instead</em> create a single <code>.hash</code> extension for <em>all</em> your hash files, whatever algorithm you use. Welcome to the unified <code>.hash</code> extension..
	</p>
	<p><img alt="an image" src="https://corz.org/windows/software/checksum/img/checksum%20document%20128.png"/><img alt="an image" src="https://corz.org/windows/software/checksum/img/checksum%20document%2048.png"/><img alt="an image" src="https://corz.org/windows/software/checksum/img/checksum%20document%2032.png"/><img alt="an image" src="https://corz.org/windows/software/checksum/img/checksum%20document%2016.png"/>
	</p>
	<p>I feel there are quite enough file extensions to deal with, and with some effort on the part of software developers, this may catch on. I hope it does, anyway, and that you agree. A single, unified hash extension looks like the way forward, to me. All comments welcome, below.
	</p>
	<p>As well as being able to verify CRC32 checksums, MD5, SHA1 and SHA256 hashes, even mixed up in the same file, checksum can also <em>create</em> such a file, if you so desire. At any rate, if you start using SHA256 or SHA1 hashes some day, you can keep your old MD5 hashes handy, <em>inside your <code>.hash</code> files.</em>.
	</p>
	<p>The single, unified hash extension gives us not only the freedom to effortlessly upgrade algorithms at any time, without having to handle yet-another-file-type, but also the ability to easily store output from multiple hashing algorithms inside a <em>single</em> <code>.hash</code> file. Welcome to multi-hashing, which will doubtless have security benefits, to boot (a multi-hash is simply <em>collision-proof</em>).
	</p>

	<h2>Legacy and cross-platform MD5/SHA1 file formats that checksum can handle..
	</h2>
	<p>If you look inside any MD5/SHA1 checksum file - it's plain text - you find all sorts of things.
	</p>
	<p>Here's what a regular (MD5) checksum file looks like..
	</p>
	<p><code>01805fe7528f0d98c<wbr/>595ba97b798717a *01 - Stygian Vista (radio controlled).mp3</code>
	</p>
	<p>Each line begins with the MD5/SHA1 digest (hash), followed by a space, then an asterisk, then the filename. It's a clear format, flexible, relatively fool-proof ("*" is not allowed on any file system), and well supported.
	</p>
	<h5>Other formats I've come across..
	</h5>
	<p><strong>single file single MD5/SHA1 hash types</strong> - these necessarily have the same name as the file, with ".md5" or ".sha1" extension added, and are often hand-made by system admins, or else piped from a shell md5/sha command) ..
	</p>
	<p><code>01805fe7528f0d98c<wbr/>595ba97b798717a</code><br/> <code>4988ae20125db8071<wbr/>43f84dbe09df978<wbr/>2c3c033a</code>
	</p>
	<p><strong>space delimited hashes</strong> (before we figured out the clever asterisk)..
	</p>
	<p><code>01805fe7528f0d98c<wbr/>595ba97b798717a 01 - Stygian Vista (radio controlled).mp3</code><br/> <code>4988ae20125db8071<wbr/>43f84dbe09df978<wbr/>2c3c033a 01 - Stygian Vista (radio controlled).mp3</code>
	</p>
	<p><strong>double-space delimited hashes</strong> (just silly, really)..<br/> <small>Believe it or not, this is the de-facto standard for md5 files, mainly because it's the output from the UNIX md5sum/sha1sum command in 'text' mode, which amazingly; is the default setting. By the way; md5sum's "-b" or "--binary" switch overrides this insanity.</small>
	</p>
	<p><code>01805fe7528f0d98c<wbr/>595ba97b798717a  01 - Stygian Vista (radio controlled).mp3</code><br/> <code>4988ae20125db8071<wbr/>43f84dbe09df978<wbr/>2c3c033a  01 - Stygian Vista (radio controlled).mp3</code>
	</p>
	<p><strong>TAB delimited hashes</strong> (I am assured these do exist!)..
	</p>
	<p><code>01805fe7528f0d98c<wbr/>595ba97b798717a	01 - Stygian Vista (radio controlled).mp3</code><br/> <code>4988ae20125db8071<wbr/>43f84dbe09df978<wbr/>2c3c033a	01 - Stygian Vista (radio controlled).mp3</code>
	</p>
	<p><strong>back-to-front hashes in parenthesis</strong> - this is quite a common format around the UNIX/Solaris archives of the world (it's the output from <code>openssl dgst</code> command) ..
	</p>
	<p><code>MD5(01 - Stygian Vista (radio controlled).mp3)= 01805fe7528f0d98c<wbr/>595ba97b798717a</code>  <small>or..</small><br/> <code>MD5 (01 - Stygian Vista (radio controlled).mp3) = 01805fe7528f0d98c<wbr/>595ba97b798717a</code>  <small>even..</small><br/> <code>SHA1(01 - Stygian Vista (radio controlled).mp3)= 4988ae20125db8071<wbr/>43f84dbe09df978<wbr/>2c3c033a</code>
	</p>
